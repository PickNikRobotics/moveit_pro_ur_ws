# Wrist Camera Recovery

## What it does, at a glance

Two host scripts for when the `wrist_mounted_camera` D415 stops publishing on hardware:

- [`scripts/relaunch_wrist_camera.sh`](../scripts/relaunch_wrist_camera.sh) works out why the camera is down and, when a relaunch can help, restarts only the wrist `realsense2_camera_node` inside the running drivers container, without a stack restart. It reads the node's launch args from the wrist include in [`cameras.launch.xml`](../src/picknik_009_ur5e_hw_config/launch/cameras.launch.xml). `--check` only diagnoses, and its exit code says which case it found (listed in the script header). `--force` relaunches a camera that is still publishing.
- [`scripts/monitor_wrist_camera.sh`](../scripts/monitor_wrist_camera.sh) is the long-running counterpart. It runs the shelf_stocking [`camera_watchdog.py`](../src/shelf_stocking/scripts/camera_watchdog.py) on the wrist colour topic, prints its state changes, diagnoses a stall with `--check` once the stall has lasted a short while, and relaunches the node itself when only the node is at fault. It keeps going across stack restarts.

They are the wrist counterpart of [`relaunch_shelf_cam.sh`](../scripts/relaunch_shelf_cam.sh) ([`zed_shelf_cam.md`](zed_shelf_cam.md)).

## Why this shape

- **Diagnose first, because a relaunch fixes only one of the failures.** A wrist D415 fails in five ways that look the same from ROS: the topic is advertised and nothing arrives. The node crashed or lost its device and stayed dead, which a relaunch fixes. The camera dropped off the USB bus (`USB disconnect` in the kernel log), which needs a replug. It re-enumerated after the container started, and the drivers container's `/dev` is a start-time snapshot ([`camera_naming.md`](camera_naming.md)), which needs a drivers restart. Its USB link is failing: the device stays listed while the kernel logs address and protocol errors on its port, which needs a different port or cable. Or it is wedged (`Frames didn't arrive`, `UVCIOC_CTRL_QUERY`), which needs a replug and then a drivers restart. The script tells these apart from the host's USB tree, the container's `/dev`, the kernel log and the relaunch log, and says which one it is rather than relaunching blindly.
- **D415s are counted, not matched by serial.** The RealSense serial in `cameras.launch.xml` is not the USB serial string, which is empty on these cameras, so sysfs cannot say which D415 is which. When one is missing, the script checks whether the scene camera still publishes to tell which one dropped.
- **The monitor relaunches the node, never the stack.** A drivers restart also drops arm control and must stay an operator's decision ([`camera_watchdog.md`](../src/shelf_stocking/design_docs/camera_watchdog.md) gives the same reasoning for reporting only). Restarting one camera node touches nothing else, and the camera is already dead when the monitor does it, so it relaunches automatically, once per outage, so a camera that a relaunch cannot fix is not restarted again and again. `AUTO_RELAUNCH=0` makes it report only.
- **It reuses `camera_watchdog.py` rather than polling with `ros2 topic echo`.** The watchdog's subscription catches a stall within seconds at no cost. A CLI poll costs a few seconds of startup and DDS discovery on every check.

## Notes and gotchas

- **Only the camera node is relaunched.** The `wrist_mounted_camera_aligned_points` `depth_image_proc` node only subscribes, so it picks the new publisher up by itself. The pkill pattern is anchored so it does not match that node. The relaunched node belongs to the script's `ros2 launch`, not the drivers launch, and a drivers restart replaces it with the normal one. Its log is in the drivers container at the path in the script.
- **The wrist and the ZED have shared a USB controller.** On 2026-11-06 the wrist D415 dropped off bus 8 (`usb 8-2: USB disconnect`), on the AMD xHCI controller (`0000:71:00.4`) that also carries the ZED, the same controller as the 2026-10-16 failure in [`camera_watchdog.md`](../src/shelf_stocking/design_docs/camera_watchdog.md). The diagnosis prints recent kernel USB events and recognises a dead host controller, which no restart of MoveIt Pro fixes.
- **A camera still listed by `lsusb` can be unreachable.** On 2026-11-06, after a replug onto the same port, the wrist D415 streamed for under a minute. Then the kernel logged `device not accepting address … error -71`, `Device not responding to setup address` and `Failed to set UVC probe control` on its port, and the RealSense driver reported its serial `NOT found` while the device was still in the USB tree. The first version of the diagnosis judged only by presence, called it a dead node and relaunched it, which cannot work. The script now treats link errors logged on a D415's port in the last few minutes as their own case and does not relaunch. `--force` overrides that, for when the link has since recovered but the errors are still inside the window. It names the controller and what else is on it, since a failing link on a shared controller points at that controller.
- **Only the container's `/dev/video*` is a snapshot.** The drivers container bind-mounts `/dev/bus/usb` live, so a camera that re-enumerated after the container started has its USB node there but not its `/dev/video*` nodes, and librealsense, which opens the video nodes, cannot see it. The diagnosis therefore checks each D415's video nodes (from its sysfs `video4linux` entries), not its USB node. An earlier version checked the USB node and reported a re-enumerated camera as reachable. [`relaunch_shelf_cam.sh`](../scripts/relaunch_shelf_cam.sh) still checks the ZED's USB node, so its re-enumeration check cannot fire.
- **A re-enumerated camera can be brought in without a drivers restart.** The drivers container is privileged, so creating the missing nodes in it (`docker exec -u root … mknod -m 0660 /dev/videoN c 81 N`, then `chgrp video`, with the numbers and modes copied from the host) lets librealsense see the camera. A wrist node that is retrying `NOT found` then picks it up by itself. That is also how to read a new camera's RealSense serial without a restart: the retrying node logs the serial and port of every D415 it enumerates, so the new one shows up beside the scene camera. The wrist camera was replaced this way on 2026-11-06, with the serial changed in `cameras.launch.xml`.
- **The diagnosis flags a D415 running at USB 2.** At 480 Mb/s the frames arrive in bursts and the Trainer's conversion stutters ([`camera_naming.md`](camera_naming.md)). That camera is not down, so the flag is only a warning.
- **Killing the monitor stops its watchdog in the container.** `docker exec` leaves the process in the container running when its client dies, so the watchdog's stdin is a pipe that only the monitor holds open, and EOF on it stops the watchdog. A watchdog started with stdin left open some other way, and whose Python then fails, sits in the container forever while reporting nothing. Check with `docker exec moveit_pro-drivers-1 pgrep -af camera_watchdog`. The monitor runs the watchdog from its path under `src/shelf_stocking/scripts/` because the submodule's `camera_watchdog.sh` expects it at `~/user_ws/scripts/`, which is true only in the standalone `shelf_stocking_ws`.
- **Never USB-reset a D415 from software** to avoid a replug: from the drivers container it knocked a wedged camera off the bus completely ([`camera_watchdog.md`](../src/shelf_stocking/design_docs/camera_watchdog.md)).

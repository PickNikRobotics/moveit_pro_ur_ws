# Scene Camera Recovery

[`scripts/monitor_scene_camera.sh`](../scripts/monitor_scene_camera.sh) runs on the host, watches the `scene_camera` D415 and the wrist Orbbec, and brings them back by itself when they drop. For the D415 it relaunches only the scene camera's RealSense node inside the running drivers container, after making the container's video device nodes match the host's; for the Orbbec it reboots the camera through its driver (see "The wrist Orbbec" below). It never restarts the drivers container and never USB-resets the camera. Its sibling for the wrist D415 is [`wrist_camera_recovery.md`](wrist_camera_recovery.md).

## Why this exists

It was written for `iq9-1`, the Qualcomm IQ-9075 board, where the board's onboard USB 3 hub resets every few minutes under collection and drops everything behind it: the scene D415 and the wrist Orbbec together. Turning off USB autosuspend and U1/U2 link power management did not stop it, and the hub's ports report no over-current. Two of the resets had no camera error before them, and the same hub dropped an Ethernet adapter before any D415 was on it, so the hub or its power is the suspect, not the camera. The hardware fix (a separately powered hub, or moving the D415 to the other USB controller) is the real cure; this script makes the outages short until then.

The two cameras recover differently. The Orbbec driver talks to the camera through `/dev/bus/usb`, which the workspace compose file bind-mounts live, and reconnects by itself. The RealSense driver on this image uses the V4L2 backend, which needs `/dev/video*`, and the drivers container's `/dev` is a snapshot taken when the container starts ([`camera_naming.md`](camera_naming.md) explains why `initial_reset` is off for the same reason). After a re-enumeration the old node keeps reading dead file descriptors, and a new one may find the camera in sysfs but fail to open a device node whose number has changed.

## Why this shape

- **Both triggers are free to poll, so outages are caught in seconds.** The D415's USB device number changes on every hub reset, and reading it from sysfs costs nothing. For a stall without a re-enumeration, a small subscriber inside the drivers container listens to the scene camera's `color/camera_info` and touches a file in the log directory the container shares with the host, and the host reads that file's age. `camera_info` rather than the image because it arrives with every frame at a few hundred bytes, where deserializing the raw image would cost real CPU on a board already loaded during collection. The first version ran a `ros2 topic echo` once a minute instead, and an outage it missed through the device-number check then lasted over a minute before recovery even started.
- **A dead frame watcher looks like a dead camera**, so a stall is only acted on after the watcher is confirmed running (it is restarted if not). It is also what tells a recovery attempt it worked, which is why it is kept alive through the attempt.
- **The device nodes are mirrored, not bind-mounted.** The container is privileged, so `mknod` inside it works. Mirroring name for name what the host has now (and removing names the host no longer has) is what librealsense needs: it finds the camera through sysfs, which is live, and then opens `/dev/videoN` by name.
- **It retries until frames come back.** A D415 often port-resets itself while its node opens it. That renumbers its video devices again, so the copy made a moment earlier is stale and the node fails with "No such device or address". On `iq9-1` this is not occasional but the rule: the first open after a hub reset fails with a UVC probe control error and the D415 is port-reset about a second later, after which the next open works. So the script waits for the camera and its video devices to stay put on the bus, gives up on an attempt the moment the device number changes or the node logs that error, and retries that case at once; other failures get a short, growing backoff. An attempt whose node comes up and sends nothing, with no renumbering and no error, is also given up on quickly: a good relaunch sends frames within a few seconds, so waiting much longer only stretches the outage (one such attempt sat out a long wait until the next hub reset happened to end it).
- **Recovery starts the node binary directly, not through `ros2 launch`.** On that board `ros2 launch` takes several seconds to start the node, which itself is up in under a second, and every outage needs at least two starts. While the node is healthy the script saves its exact command line and copies of its parameter files, and recovery reruns that. Taking them from the running node (normally the drivers launch's own) keeps the relaunched node identical to it; the `cameras.launch.xml` parse is the fallback for when nothing has been saved yet in this container's lifetime.
- **It does not send the port reset itself** to skip the doomed first open, even though that would save a few seconds. A software `USBDEVFS_RESET` once left a wedged D415 off the bus until a physical replug (`src/shelf_stocking/design_docs/camera_watchdog.md`), which is far worse than one failed attempt. This is why the wrist monitor's "relaunch once per outage" rule does not carry over.
- **The launch args come from `cameras.launch.xml`**, from the `scene_camera` include, so the relaunched node cannot drift from the one the drivers launch starts. Only `$(var ...)` references that include uses must resolve. That is deliberate: `relaunch_wrist_camera.sh` requires every `let` in the file to have a condition it understands, and since the Orbbec preset `let` was added it stops before doing anything.

## The wrist Orbbec

The same script watches the wrist Orbbec too, because on `iq9-1` every hub reset drops both cameras. It needs no device-node copy (its driver uses `/dev/bus/usb`, which is live), so its recovery is the one [`orbbec_wrist_camera.md`](orbbec_wrist_camera.md) prescribes: the driver's `reboot_device` service. What differs from `orbbec_stream_watchdog.py` is the timing. That watchdog judges a stall after a longer wait and doubles its grace after every reboot that brings no frames, which is right for a camera that is unplugged, but during a run of hub resets it left the wrist camera dark for minutes. The script reboots after a few seconds without frames and then at a fixed interval, and when the Orbbec is not on the USB bus at all it says it needs a replug instead of calling the service.

Two watchdogs rebooting one camera lengthen every outage (the second reboot lands while the first is reconnecting), so the script stops the drivers launch's `orbbec_stream_watchdog` in the running container, after reading its watch topic and reboot service from that node's parameters so it follows `cameras.launch.xml` (dual colour or not). A drivers restart starts the watchdog again and the script stops it again. With the script not running, the stack is back to the built-in watchdog alone.

The two cameras are watched by separate loops, so a long scene camera recovery does not delay a wrist reboot.

## Notes and gotchas

- **A stack restart is a new container, not a stopped one.** `moveit_pro run` can replace the drivers container fast enough that a "is it running?" poll never sees it down, and the replacement has none of the script's `/tmp` helpers or frame watchers. So each loop pins the container instance (ID and start time) it set up, and starts over as soon as that changes. The start-up grace is likewise counted from the container's start, not the script's, so a script restarted beside an old stack does not sit out a grace period it does not need.

- **The relaunched node belongs to the script's `ros2 launch`, not the drivers launch.** A drivers restart replaces it with the normal one; the script waits out the restart and then watches the new node.
- **A relaunched node's log is size-capped, and the node is stopped when it passes the cap.** A node left holding a D415 that has gone off the bus logs a `VIDIOC_QBUF` error per frame request, tens of MB a second, and the relaunched node outlives the script (it is not the drivers launch's child). With the script gone and nothing watching, one such node once filled the disk. A healthy node logs a few KB, so the cap only ever stops a stuck one; if the script is still running it relaunches the camera as for any other outage. The cap is `LOG_MAX_BYTES` in the script.
- **librealsense may still USB-reset the D415 from its own error path** while a node fails to open it. The script does not ask for that and cannot stop it.
- **On aarch64 the RealSense point-cloud filter is named `pointcloud__neon_`**, so the include's `pointcloud.enable` does nothing there and no `depth/color/points` topic is published on that board, from either the normal or the relaunched node. The colour image and aligned depth are unaffected.
- **Run it as a systemd user service**, not with `nohup`: a `nohup` copy dies with every reboot, and on `iq9-1` reboots are part of normal work. A user unit with `Restart=always` and `WantedBy=default.target`, plus lingering for the user (already on for the Desktop App's discovery socket), starts it at boot and brings it back if it exits; its output goes to the user journal. Do not stop it with `pkill -f monitor_scene_camera.sh` from inside an `ssh host '…'` command line: the pattern also matches that command line and kills the SSH session.

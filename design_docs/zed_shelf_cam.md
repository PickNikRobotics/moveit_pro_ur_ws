# Zed Shelf Cam

## At a glance

**`shelf_cam` is a Stereolabs ZED 2i, fixed in the cell and looking at the shelving. It is a third, HW-only camera next to the two RealSense D415s.**
- [`cameras.launch.xml`](../src/picknik_009_ur5e_hw_config/launch/cameras.launch.xml) starts it through [`pro_zed_launch.py`](../src/picknik_009_ur5e_hw_config/launch/pro_zed_launch.py).
- That wrapper includes `zed_wrapper`'s own launch file and maps the ZED topics onto the `/camera/<name>/...` layout of [`camera_naming.md`](camera_naming.md).
- Parameters that differ from the `zed_wrapper` defaults are in [`zed_shelf_cam.yaml`](../src/picknik_009_ur5e_hw_config/config/zed_shelf_cam.yaml).
- Its pose in the world comes from the board calibration: [`board_based_calibration.md`](board_based_calibration.md), stage c.

The driver is two git submodules under `src/external_dependencies/`: `zed-ros2-wrapper` and `zed-ros2-interfaces`. They are an explicit, approved exception to the "never touch external_dependencies" rule.

## Why this shape

- **The topic layout is matched by configuration, not by nature.** The RealSense driver publishes `/camera/<name>/...` natively; the ZED does not.
  - The wrapper remaps the ZED's native topics.
  - It also sets the depth image to millimetre integers, so a consumer written against the D415 does not misread ZED depth by a factor of a thousand.
  - Topic names and payload types are coupled: change one only with the other.
- **The color topic carries the rectified left image.** It is paired with the rectified image's `camera_info`, which is consistent for pose estimation. It is the wrong input for an intrinsic calibration, which wants a raw image.
- **The ZED publishes only its own link tree.** Positional tracking and its odom/map transforms are off. The root link (`shelf_cam_camera_link`) gets its parent, `world`, from the calibration YAML and `PublishStaticTransform`, the same pattern as `scene_camera_link`.
- **Submodule versions follow the SDK baked into the image, not the host.** The wrapper, the interfaces and the SDK are one matched set, and the [`Dockerfile`](../Dockerfile) is where the SDK comes from.
  - `zed-ros2-wrapper` is on the `v5.4.1` tag, matching the ZED SDK 5.4.1 that the `Dockerfile` installs. A wrapper from another SDK line compiles against the wrong `sl::` API.
  - `zed-ros2-interfaces` provides `zed_msgs`, which is not packaged for Jazzy. It is on `5.3.0`, the newest release older than the wrapper tag, which provides every message and service the wrapper uses.
  - The SDK's CUDA major has to match the base image's CUDA runtime. Bump the three together, and re-check the base image's CUDA when MoveIt Pro is upgraded.
  - These replace the 4.2-line versions staged on the Agent PC, whose SDK 4.2 was installed on the host and provisioned into a dev container by hand.
- **This re-creates Kristen's uncommitted design from the Agent PC.** It keeps the same remaps, the same parameter choices and the same CI skip. It differs in three places:
  - the calibration parameter file and the `launch_shelf_cam` switch;
  - no `exec_depend` on `zed_wrapper` (see below);
  - the TF parent.

## Notes and gotchas

- **The ZED drops off USB and then cannot be opened.** Every stack start resets its HID interface (kernel: `usb 7-1.2: reset full-speed USB device`), and on 2026-11-02 it also disconnected outright and re-enumerated. After that the ZED SDK reported `CAMERA NOT DETECTED` on every open, and the component container exited, although the drivers container had the camera's current device nodes and the right permissions. Nothing respawns it, so the `shelf_cam` topics just stop, and a Trainer episode recorded meanwhile has no shelf camera at all (its observed rate in the Trainer reads low, because one configured camera is missing). [`scripts/relaunch_shelf_cam.sh`](../scripts/relaunch_shelf_cam.sh) relaunches only the ZED. That fixes a node that crashed, but not a camera that is wedged (replug, then restart the drivers container, because the replug gives it new device nodes the container's start-time `/dev` lacks) or one that re-enumerated after the container started (restart the drivers container). Repeated drops point at the cable, a hub or USB power. Two traps when relaunching by hand: run the node as the user **by name** (`docker exec -u <name>`), because `-u <uid>:<gid>` drops the supplementary `video` group and the SDK then reports the unreadable `/dev/video*` as `CAMERA NOT DETECTED`, exactly like a wedged camera; and never kill a ZED node that is still opening the camera after a stack start (it takes a few seconds), which leaves the camera unopenable for a while. The script handles both: it does nothing while the camera publishes, and waits for a node that started under a minute ago.

- **The SDK is installed by the image build, not taken from the host.** The `Dockerfile`'s `base` stage installs it, together with the CUDA compiler and cudart dev files its CMake config needs: the base image ships the CUDA runtime only. A host SDK is irrelevant to the container, and its version need not match. The installer is a large download, so a cold image build is slow; the layer is cached afterwards. The install and a `find_package(ZED)` link were checked in a throwaway container from the 10.2 base image; the full `zed_components` compile and a camera open have not been run yet.
- **The SDK installer must not run its Python step.** By default it pip-installs `pyzed`, `Cython` and a newer `numpy` over the base image's own `numpy`, with permissions only root can read. The first message package to generate Python bindings then fails with `numpy/core/include: Permission denied`, which looks like a bug in whichever package colcon happened to start first (it was `epick_msgs`). The `Dockerfile` passes `skip_python`; nothing here uses `pyzed`.
- **The build container has no GPU, so `zed_debug` is ignored.** The colcon build runs in the `base` service, which the NVIDIA compose file does not give a GPU, so `libcuda.so.1` is absent at link time. The SDK's shared libraries need it. `zed_components` builds only shared libraries, which link anyway. `zed_debug`, new in the 5.x wrapper, links an executable and cannot, so [`colcon-defaults.yaml`](../colcon-defaults.yaml) ignores it and CI skips it. Nothing uses it.
- **The color topic is relayed to `rgb8`; the ZED never publishes it directly.** The wrapper only publishes BGR (`bgra8`, or `bgr8` with `enable_24bit_output`), and the Trainer's LeRobot converter reshapes raw images by channel count without reordering them: `bgra8` fails to convert outright and `bgr8` converts with red and blue swapped, silently. So `pro_zed_launch.py` remaps the ZED's color image to an internal `color/image_bgr` topic and starts [`rgb_image_relay.py`](../src/picknik_009_ur5e_hw_config/scripts/rgb_image_relay.py), which republishes it as `rgb8` on `color/image_raw`, the encoding the RealSense driver uses natively. `camera_info` is not relayed; its stamp and frame match. Anything that reads `color/image_raw` (the Trainer, calibration) now sees `rgb8`. Episodes recorded before the relay carry `bgra8` and do not convert.
- **The 5.x wrapper renamed the RGB topics.** The rectified color image is `rgb/color/rect/image`, with its `camera_info` beside it; depth and the point cloud kept their names. A remap whose source no longer exists fails silently: the shelf color topic never appears and the Trainer refuses every recording. Check the remap table in `pro_zed_launch.py` against the wrapper on every bump.
- **`depth_mode: 'ULTRA'` is deprecated in SDK 5.** It still works and needs no AI model, which is why it is kept. If a later SDK removes it, the wrapper falls back to `NEURAL` with only a warning, and the first launch then downloads and optimizes a model.
- **The camera's factory calibration is downloaded on every fresh container.** The SDK fetches it from Stereolabs by serial number into `/usr/local/zed/settings/`, which the image hands to the container user. The container is recreated on every launch, so the drivers host needs internet access when the ZED opens.
- **`picknik_009_ur5e_hw_config` does not `exec_depend` on `zed_wrapper`, on purpose.** colcon refuses `--packages-skip` for a workspace package that another package depends on. CI cannot build the ZED packages, so it skips them ([`ci.md`](ci.md)), and that only works without the dependency.
- **The camera's collision body is a plain box, not the wrapper's mesh.** [`shelf_cam.urdf`](../src/picknik_009_ur5e_config/description/shelf_cam.urdf) holds one box, sized from the measured enclosure, centred on the wrapper's camera body centre. `Load Calibrated Scene` adds it with `AddURDF` at the stage c pose, the same way it adds the scene camera body. Its axes follow the ZED root link: depth along the viewing axis, width along the stereo baseline, height up from the mount. It sits inside the same optional block as the `shelf_cam` transform, after the transform, so it is skipped when the stage c file is missing. Its link has its own name, so it cannot clash with the frames the ZED driver publishes. A new URDF needs one rebuild before `AddURDF` can find it.
- **`launch_shelf_cam`** turns the camera off on a host without the SDK or the camera.
- **One override file only.** `zed_wrapper` takes a single `ros_params_override_path`, so the calibration file repeats the normal overrides. Keep [`zed_shelf_cam_calibration.yaml`](../src/picknik_009_ur5e_hw_config/config/zed_shelf_cam_calibration.yaml) in step with `zed_shelf_cam.yaml`.
- **Calibration resolution.** At the wrapper's default, downscaled resolution the calibration board is too small to detect from the ZED's distance. The calibration file selects full resolution with no downscale ([`board_based_calibration.md`](board_based_calibration.md)).
- **Distance to the board limits stage c.** Even at full resolution, the ZED must be close enough to the board on the back wall. The farthest usable distance and the steepest usable viewing angle for the current board are in the camera sizing table kept with the calibration report. Moving the ZED needs no Objective change, only a re-run of stage c.
- **`SetRemap` reaching a composable node depends on the `launch_ros` version.** If the ZED topics appear under their native `/shelf_cam/zed_node/...` names, check that first.
- **Sim counterpart.** `picknik_009_ur5e_config_sim` has the ZED as the MJCF camera `shelf_cam_left_camera` with its box body, at the calibrated pose, publishing on the same topics as the hardware ([`camera_naming.md`](camera_naming.md)). It renders a 4:3 frame with the real focal length, and its depth is the plugin's, not the ZED SDK's.
